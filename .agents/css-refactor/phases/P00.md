#### Deviation from the brief — Preflight is NOT imported (read this before Phase 1)

The plan's §2.1 says `@import "tailwindcss"`. That pulls Tailwind's Preflight,
which in v4 lives inside `@layer base` (verified in
`node_modules/tailwindcss/index.css`). Because every existing stylesheet in this
repo is **unlayered**, unlayered rules beat any layered rule regardless of
specificity — so Preflight can never override `globals.css` / `admin.css` /
`super-admin.css` / `owner-workspace.css`. But it *would* still apply wherever
no existing rule sets the property at all, and Preflight's
`*{margin:0;padding:0}` plus `h1–h6{font-size:inherit;font-weight:inherit}`
would strip UA defaults on elements outside `.soa` / `.ad-root` coverage
(`.ad-root` styles only h1/h2/h3 — an `<h4>` would collapse). That is a visual
change, i.e. a Phase 0 defect.

So `app.css` imports the theme and utilities layers directly — Tailwind's
documented way to opt out of Preflight:

```css
@layer theme, base, components, utilities;
@import "tailwindcss/theme.css" layer(theme);
@import "tailwindcss/utilities.css" layer(utilities);
@source "../";
```

Verified empirically with `npx @tailwindcss/cli`: utilities generate
(`bg-brand`, `border-line-2`, `rounded-card`, `font-display` all emit),
`@source "../"` detects sources correctly (it is required — automatic source
detection is not inherited when you skip the `tailwindcss` entrypoint), and the
output contains zero Preflight rules. **Border utilities do not depend on
Preflight** — v4 emits `border-style: var(--tw-border-style)` with an
`@property` default of `solid`, confirmed in the generated CSS — so nothing
downstream is blocked by this. Adopting Preflight is a deliberate, diffable
change that should happen in a later phase *with the screenshot baseline in
hand*, not blind in Phase 0.
